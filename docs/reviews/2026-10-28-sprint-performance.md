# Sprint 启动与刷新性能

范围：减少 Sprint 只读渲染的重复工作，保留当前界面与任务语义。基线为 f1c1c1d。
包工作区开始时干净；父配置已有修改未纳入。本轮没有改写用户 Org、SQLite 或历史快照。
此文记录 0ab45b8 的单次渲染优化；后续跨刷新复用见 [源缓存记录](2026-10-28-sprint-source-cache.md)。

## 原因与修改

实际会话单栏渲染中，projects 的文件归属检查每次都重新获取 Agenda 文件，
并对所有路径调用 file-truename。递归路径调用计数约 36,470，org-agenda-files
计数 1,300；项目识别还先检查文件归属，再排除非一级标题。随时与项目摘要
分别调用 collect，产生两次完整项目扫描。这里的耗时不来自缓存失效，而是没有复用
同一次渲染中已经确定的文件归属与项目列表。

采用现有动态绑定边界，不增加持久缓存、后台预热、计时器、advice 或用户选项：

- sources 的 source-agenda-file-p 统一 core／projects 的文件归属判定，保留真实路径和别名语义。
- workbench-view 为一次渲染创建路径／归属快照，单个文件的否定结果也复用。
- projects-collect 在同一渲染内只扫描一次，随时与项目摘要复用结果。
- 项目与阶段识别先检查层级，再做文件归属检查，提前排除不可能匹配的节点。

缓存退出渲染即释放；每次打开／redo 从当前 Agenda 配置和源 buffer 重新读取。
修改命令、后台 source-read、Org element cache 的原有策略不变。
双栏各自渲染时各有快照，不跨两个可能经历用户编辑的渲染保存来源位置。

维护入口是 agenda-view 的 workbench-view、sources 的 source-agenda-file-p，
以及 projects 的 collect／--collect。若扩展渲染时仍须保持只读，不能把缓存边界移到
任务编辑或持久工作台生命周期中。撤回本次提交即可恢复原读取路径。

## 验证

先增加行为与调用计数回归，再运行官方隔离 runner。修改前两个性能断言失败：
一个项目被扫描两次，样本的 org-agenda-files 被调用 96 次。
修改后同一样本项目只扫描一次，文件查询少于 25 次。

新增 6 项 ERT，覆盖渲染复用、未保存的项目改名与完成进度、下次渲染替换 Agenda
文件集合、符号链接别名、渲染之外即时读取配置，以及失败渲染释放缓存。
最终官方全套 822/822 通过，无排除项；编译通过，checkdoc 0 警告。
全新安装、惰性 require、模式启用／停用 smoke 通过。

当前 Emacs 31.1／Org 9.8.10 会话中，保留源 buffer，在临时输出 buffer 比较
优化前与临时编译后的相关函数，各 7 次。整个测量结束恢复原函数；源 buffer 的
buffer-chars-modified-tick 均未改变。

| 测量 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 单栏内容渲染中位数 | 725 ms | 191 ms |
| org-agenda-files 调用次数 | 1,300 | 9 |
| file-truename 递归调用次数 | 36,470 | 291 |

内容渲染中位数减少约 74%。计时包含正常 GC 波动；函数包装统计为包含子调用的耗时，
不能相加当作总时间。这里没有测量真实窗口布局、字体渲染或第一次访问文件的宿主 hooks。

另以 4 个临时 Area、12 个项目、24 个阶段、240 个任务验证原生 org-agenda "d"
与 org-agenda-redo。使用分别从基线与修改版编译的完整包、相同依赖及隔离测试 profile。
在完整回归结束后按前后顺序运行，首次原生打开为 446 → 276 ms（减少约 38%），
随后 5 次 redo 的中位数为 257 → 104 ms（减少约 60%）。
两版输出文本归一化临时文件名后 SHA-256 完全相同：
7a09422d7f1ecbb3444b0c14576f1834ace86850a0108460c227ce7b86d00740。
样本不包含宿主图形主题、Vulpea 文件访问集成或真实鼠标交互，不能作为整套 Emacs
冷启动的加速承诺。
